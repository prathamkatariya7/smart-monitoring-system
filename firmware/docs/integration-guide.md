# Reactor Monitoring Platform — Firmware Integration Guide

**Audience:** ESP32-P4/C6 firmware team (Arduino IDE).
**Status:** derived directly from the backend's actual implementation and
verified behaviour (not from the original design document), as of 2026-11-07.
Where the server has a documented *intent* that isn't live yet, it is called
out explicitly in **Known gaps** — do not build firmware logic against those
until this doc is updated to say they're active.

This document describes the **wire contract** your firmware must speak to
talk to the Reactor Monitoring Platform backend: MQTT topics, payload JSON
shapes, TLS/identity requirements, and the device-claim handshake. It does
not cover the DWIN display UART protocol (that's internal to the ESP32
firmware) or anything about the web UI.

---

## 1. Overview

Each physical device (ESP32-P4 + C6, one per reactor control box) is
represented server-side by a `device` row, identified by a server-generated
UUID (`deviceId`) once it has been **claimed**. Before claim, the device only
needs its factory-assigned `serialNo`; after claim, every MQTT topic the
device uses is namespaced by its `deviceId`, not its serial number.

High-level flow:
1. Device is claimed (binds `serialNo` → `deviceId`) via the backend's REST
   API — this is a one-time admin action, not something firmware does over
   MQTT. See [Section 3](#3-device-identity--claim-flow).
2. Device is bound to a reactor (`equipment`) record — also an admin REST
   action. **A device that is claimed but not bound will have its telemetry
   silently dropped by the server** (see [Section 7](#7-idempotency--gap-detection)).
3. Device connects to the MQTT broker over mTLS, publishes `state` (birth
   message) and `event` (e.g. `TIME_ANCHOR`), then streams `tele/batch`
   messages.
4. Server acks each batch (`ack/data`), detects sequence gaps, and may push
   commands (`cmd/{name}`) the device must execute and acknowledge
   (`ack/cmd`).
5. Server pushes a retained `cfg/desired` bundle whenever the device's
   configuration changes (binding, policy pack, feature switches).

## 2. Transport & Security

- **Broker:** Eclipse Mosquitto 2.x, MQTT **v5** required (the correlation-data
  property used for command/ack matching is an MQTT5 feature — see
  [Section 6](#6-cmdcmd-server--device)).
- **Port:** 8883 (TLS) inside the Docker network. In this dev/pilot
  deployment the host-mapped port is `18883` (chosen to dodge a Windows
  Hyper-V port-exclusion issue) — on real deployed hardware talking to the
  broker over the LAN, use whatever port the network team configures; it
  will be the standard 8883 unless told otherwise.
- **mTLS is mandatory.** The broker is configured with:
  ```
  require_certificate true
  use_identity_as_username true
  allow_anonymous false
  ```
  Every device **must** present a client certificate signed by the
  platform's CA at connect time. There is no username/password fallback —
  an unauthenticated or wrong-CA connection is rejected outright.
- **Certificate provisioning is not yet automated.** In this repo/pilot,
  device certificates are generated by a dev script (not a factory HSM
  pipeline). For now, assume each device ships with:
  - A client certificate + private key signed by the platform CA.
  - A CA certificate to validate the broker's own server certificate.
  - The certificate's Common Name (CN) is **intended** to equal the device's
    `deviceId` (UUID) once claimed — but see **Known gaps**: this convention
    is not currently enforced by the broker, so firmware should not depend
    on the broker rejecting a mismatched cert/topic combination yet.
- **TLS hostname verification:** when connecting from firmware, verify the
  broker's server certificate against the CA, and connect using whatever
  hostname/IP is in the server certificate's SAN list (the dev cert includes
  `mosquitto`, `localhost`, `127.0.0.1` — production certs will need the
  real broker hostname/IP added to their SAN list by whoever issues them).

## 3. Device Identity & Claim Flow

Claiming is a **REST API action performed by an admin**, not something
firmware initiates over MQTT. Firmware's job is simply to know its own
`serialNo` (and ideally report `hwRevision`/cert info to whoever runs the
claim step).

`POST /api/v1/devices/claim` (Admin JWT required), body:
```json
{
  "serialNo": "DEV-0001",
  "claimCode": "a factory-printed or provisioning-time secret",
  "hwRevision": "optional free-text hardware revision",
  "certSerial": "optional — the issued client cert's serial number"
}
```
- `claimCode` must match what's on record for that `serialNo` (or, for a
  brand-new serial, whatever is supplied becomes the on-record code — see
  **Known gaps**, this auto-registration is a dev convenience).
- On success, the response includes the device's `id` (UUID) — **this is the
  `deviceId` used in every MQTT topic from then on.** Whoever provisions the
  device needs to configure this UUID into the firmware (e.g. via a
  provisioning UART command, QR code, or NVS write at claim time) — there is
  currently no MQTT-based "ask the server for my UUID" mechanism.
- After claiming, the device must also be **bound** to a reactor
  (`POST /devices/:id/bind`) before any telemetry it sends will be stored.
  This is also an admin REST action.

## 4. Topic Reference

All topics are rooted at `rmp/v1/{deviceId}/...`, where `{deviceId}` is the
UUID obtained at claim time (Section 3) — **not** the serial number.

| Topic | Direction | QoS | Retained |
|---|---|---|---|
| `rmp/v1/{deviceId}/state` | device → server | 1 | no (server does not require retain, but devices may retain their last state if useful on reconnect — not required) |
| `rmp/v1/{deviceId}/tele/batch` | device → server | 1 | no |
| `rmp/v1/{deviceId}/tele/backlog` | device → server | 1 | no |
| `rmp/v1/{deviceId}/event` | device → server | 1 | no |
| `rmp/v1/{deviceId}/ack/data` | server → device | 1 | no |
| `rmp/v1/{deviceId}/cmd/{cmd}` | server → device | 1 | no |
| `rmp/v1/{deviceId}/ack/cmd` | device → server | 1 | no |
| `rmp/v1/{deviceId}/cfg/desired` | server → device | 1 | **yes** |

Notes:
- `tele/backlog` uses the **exact same payload shape** as `tele/batch` — use
  it specifically for buffered/backfilled data the device is replaying after
  a reconnect (e.g. samples collected while offline), so the server can
  track that distinction internally. Functionally the server processes both
  identically today (same handler), but the topic separation is meaningful
  for future server-side handling — always use `backlog` for replayed data,
  `batch` for live data.
- `cfg/desired` is **retained**, so a device that (re)connects and
  subscribes will immediately receive the last-pushed config even if the
  server doesn't happen to be processing a binding change at that exact
  moment. Subscribe to it on every connect.
- `{cmd}` in `cmd/{cmd}` is a literal command name, e.g. `cmd/set_calibration`
  — subscribe with a wildcard: `rmp/v1/{deviceId}/cmd/+`.

## 5. Payload Schemas (device → server)

### 5.1 `state` (birth/status message)
```json
{ "online": true, "link": "eth", "boot": 1, "fw": "1.0.0", "ts": 1730972400000 }
```
| Field | Type | Required | Meaning |
|---|---|---|---|
| `online` | bool | yes | `true` on connect; firmware should also publish `online:false` as a **last-will** message if the MQTT client library supports LWT, so the server can detect ungraceful disconnects. |
| `link` | `"eth"` \| `"wifi"` \| `"none"` | no | Current network interface in use. |
| `boot` | integer | no | Boot/epoch counter — increment on every power-on/reset. **This must change on every reboot**, because the server uses it to decide whether to reset sequence-gap tracking (Section 7). |
| `fw` | string | no | Firmware version string, free-form. |
| `ts` | integer (ms) | no | Device's current UTC time in epoch milliseconds — **omit this field entirely if the device clock is not synced to real time.** |

### 5.2 `tele/batch` / `tele/backlog` (columnar sample batch)
```json
{
  "v": 1,
  "boot": 1,
  "attempt": null,
  "cal": 1,
  "fw": "1.0.0",
  "link": "eth",
  "tsync": 1,
  "f": ["seq", "mono", "ts", "t", "t_raw", "rpm", "tq", "q", "flt", "fl"],
  "d": [
    [1000, 1000, 1730972400000, 35.2, 35.6, 400, 12.5, "GGG", 0, 0],
    [1001, 2000, 1730972401000, 35.3, 35.7, 400, 12.5, "GGG", 0, 0]
  ]
}
```
**Envelope fields:**
| Field | Type | Required | Meaning |
|---|---|---|---|
| `v` | integer | yes | Batch schema version. Use `1`. |
| `boot` | integer | yes | Same boot/epoch counter as in `state`. |
| `attempt` | string (UUID) or `null` | no | The `process_attempt` UUID this data belongs to, if the device knows it (e.g. was told via a command or config push). `null` if unknown — the server will still accept and store the sample, just without a process linkage. |
| `cal` | integer | no | The `calibration_version` number currently applied on-device. |
| `fw` | string | no | Firmware version. |
| `link` | `"eth"` \| `"wifi"` \| `"none"` | no | — |
| `tsync` | `0` or `1` | **yes** | `1` = device clock is synced to real UTC and the `ts` column values are authoritative. `0` = device clock is not synced; the server will fall back to its own receipt time and flag every row `TIME_UNSYNCED` (Section 6.1). **Always set this honestly** — do not send `1` with a guessed/unsynced clock. |
| `f` | string[] | yes | Column-name header. Any subset/order of the known column codes below is acceptable — the server looks columns up by name, missing columns are simply not recorded for that batch. |
| `d` | array of arrays | yes | One row per sample; each row's values are positioned according to `f`. |

**Known column codes (use any subset, in any order, as columns in `f`):**
| Code | Type | Meaning |
|---|---|---|
| `seq` | integer | Sequence number **within the current `boot`** — must increment by exactly 1 per sample with no device-side renumbering. Used for gap detection (Section 7). Resets to any starting value on reboot (paired with a new `boot` value). |
| `mono` | integer (ms) | Device monotonic uptime counter at sample time. Does not need to relate to wall-clock time — just needs to be monotonic within a boot. |
| `ts` | integer (ms) | Device's believed UTC epoch time for this sample. Only trusted by the server if `tsync == 1`. |
| `t` | float | Corrected/calibrated temperature, °C. |
| `t_raw` | float | Raw (pre-calibration) temperature, °C. |
| `rpm` | float/int | Stirrer speed. |
| `tq` | float | Torque, N·cm. |
| `q` | string | Per-channel quality, **one character per channel**, each one of `G` (good), `S` (suspect), `B` (bad) — e.g. `"GGG"` for 3 good channels. See Section 8 for encoding. |
| `flt` | integer | Device fault code (small integer, device-defined meaning). |
| `fl` | integer | Per-row flag **bitmask** set by the device — see Section 6.1 for the bit layout. Device-settable bits: `LATE_CYCLE`(1), `TIME_ESTIMATED`(4), `TIME_DERIVED`(8), `POST_PLANNED`(32), `STARTED_OFFLINE`(64), `LINK_DOWN`(128). The server ORs in its own bits (`TIME_UNSYNCED`, `GAP`) on top of whatever the device sends. |

Any column not included in `f` is simply recorded as absent (null) for that
batch — e.g. a device with only a single temperature channel and no torque
sensor should just omit `tq` from `f` entirely rather than sending zeros.

### 5.3 `event` (discrete occurrences)
```json
{ "type": "TIME_ANCHOR", "boot": 1, "ts": 1730972400000, "mono": 1000 }
```
| Field | Type | Required | Meaning |
|---|---|---|---|
| `type` | string | yes | Free-form event type. The server currently special-cases exactly one value: `"TIME_ANCHOR"` (see below). Any other string is accepted and stored verbatim (e.g. `"DEVICE_REBOOT"`, `"NET_FAILOVER"`) but has no special server-side behaviour yet. |
| `boot`, `ts`, `mono` | — | no | Same meaning as in `tele/batch`. |
| `offline_origin` | bool | no | Set `true` if this event is being reported late (device was offline when it actually happened). |
| *(anything else)* | — | — | Any additional fields you include are stored as-is in the server's audit record for the event — useful for free-form diagnostic payloads. |

**`TIME_ANCHOR`:** send this once the device successfully syncs its clock
(e.g. via NTP, or a server-provided time anchor by whatever mechanism your
firmware uses). On receipt, the server marks the device's `clockSource` as
`NTP` and records the sync timestamp. **This does not retroactively fix
already-ingested unsynced samples** — see Known gaps.

## 6. Payload Schemas (server → device)

### 6.1 `ack/data`
```json
{ "boot": 1, "upto_seq": 1009 }
```
Sent once per processed batch (not per sample). `upto_seq` is a **high-water
mark**: the highest `seq` value the server has now accounted for, *including*
any gap it detected but could not recover (the data is gone — the ack just
tells the device it's safe to free that ring-buffer space). Do not treat this
as per-sample delivery confirmation.

**FLAG_BITS reference** (the `fl` column / server-stored `flags`):
| Bit | Value | Set by | Meaning |
|---|---|---|---|
| `LATE_CYCLE` | 1 | device | Sample reported later than its normal cycle. |
| `TIME_UNSYNCED` | 2 | **server** | Set automatically whenever the batch's `tsync` was `0`. |
| `TIME_ESTIMATED` | 4 | device | Device estimated this sample's timestamp. |
| `TIME_DERIVED` | 8 | device | Timestamp derived from another anchor, not directly measured. |
| `GAP` | 16 | **server** | Set automatically when a sequence gap was detected immediately before this sample. |
| `POST_PLANNED` | 32 | device | Sample taken after the process's planned end. |
| `STARTED_OFFLINE` | 64 | device | Device started this recording session while offline. |
| `LINK_DOWN` | 128 | device | Network link was down at sample time. |

Device-set bits are OR'd through unchanged; the server only ever adds
`TIME_UNSYNCED`/`GAP` on top, never clears device-set bits.

### 6.2 `cmd/{cmd}` (command envelope)
```json
{ "id": "a1b2c3d4-...", "cmd": "set_calibration", "version": "...", "channel": "temp1", "method": "two_point", "coefficients": { "a": 1.02, "b": -0.4 } }
```
- `id` is a server-generated command UUID. It is also carried as the **MQTT5
  `correlationData` property** on the publish — if your MQTT client library
  exposes MQTT5 user properties/correlation data, prefer reading it from
  there; the `id` field in the JSON body is a fallback for tooling that
  doesn't expose MQTT5 properties, but both always carry the same value.
- Everything besides `id`/`cmd` is command-specific payload. The only
  command currently sent by the backend is `set_calibration` (shape shown
  above: `version`, `channel`, `method`, `coefficients: {a, b}` where the
  device should apply `corrected = a * raw + b`). The command dispatcher is
  generic, though — any `cmd` name/payload can be sent via the admin API, so
  firmware should handle unrecognized `cmd` values gracefully (reply
  `ack/cmd` with `status: "rejected"`, don't crash).

### 6.3 `ack/cmd` (device → server, in response to 6.2)
```json
{ "id": "a1b2c3d4-...", "status": "applied", "applied_version": 1 }
```
| Field | Type | Required | Meaning |
|---|---|---|---|
| `id` | string | **yes** | Must exactly match the `id` from the `cmd/{cmd}` message being acknowledged. If this is missing or doesn't match a command the server knows about, the ack is silently dropped (logged, no error sent back). |
| `status` | `"applied"` \| `"rejected"` | yes | — |
| `applied_version` | integer | no | For `set_calibration`, echo back the calibration version actually applied. |
| `reason` | string | no | Free text, useful when `status: "rejected"`. |
| *(anything else)* | — | — | Stored verbatim in the server's command record. |

### 6.4 `cfg/desired` (retained config bundle)
```json
{
  "version": 3,
  "policyPack": "flexible",
  "featureSwitches": { "someFeature": true },
  "binding": { "equipmentId": "...", "laboratoryId": "...", "reactorNumber": "R-12" },
  "laboratoryName": "Main Lab",
  "thresholds": null,
  "alertCatalog": null,
  "calibration": null,
  "network": null
}
```
Subscribe to this **retained** topic on every connect so you always have the
latest config, even if nothing changed recently. `version` increases
monotonically each time the server pushes a new bundle — use it to detect
whether you've already applied the current config. `binding` is `null` if
the device currently has no open binding to a reactor (telemetry will be
dropped server-side in that state — see Section 7). **The four `thresholds`/
`alertCatalog`/`calibration`/`network` fields are permanently `null` in the
current backend** — they're reserved for future use; do not build firmware
logic that expects them to ever be populated until this doc says otherwise.

## 7. Idempotency & Gap Detection

- **Deduplication:** each sample is keyed by `(ts, deviceId, boot, seq)`. If
  you redeliver the exact same batch (e.g. after a QoS-1 retry that the
  device wasn't sure was received), the server silently discards the
  duplicates rather than double-counting — safe to retry sends.
- **Gap detection:** the server tracks the last `seq` it saw per device, per
  `boot`. If a new sample's `seq` is more than 1 greater than the last seen
  (within the *same* `boot`), the server logs a gap and flags that sample
  `GAP`. **Changing `boot` resets gap tracking** — i.e., rebooting and
  starting again at `seq=0` (or any value) under a new `boot` number is the
  correct way to signal "this is a fresh sequence," not a gap.
- **Unbound/unclaimed devices:** if a `tele/batch` arrives for a `deviceId`
  the server doesn't recognize, or for a device that has no **open**
  `device_binding` (i.e., not currently assigned to a reactor), the entire
  batch is dropped with a server-side warning log — no error is sent back to
  the device over MQTT. If your device seems to be publishing successfully
  but data never appears in the system, the most likely cause is a missing
  claim or binding, not a protocol error.

## 8. Quality & Fault Codes

The `q` column in `tele/batch` is a string with **one character per
measurement channel**, in a fixed, device-defined channel order (e.g. if a
device has 3 channels, always send exactly 3 characters, in the same order
every time):
- `G` — Good: value is trustworthy.
- `S` — Suspect: value may be inaccurate (e.g. sensor marginal, out-of-range
  but still numeric, warming up).
- `B` — Bad: value should not be trusted / treat the channel as failed for
  this sample.

The `flt` column is a free-form small integer fault code — its specific
value-to-meaning mapping is device/firmware-defined; the server stores it
as-is and does not currently interpret it.

## 9. Known Gaps — Do Not Assume These Are Active

These are explicitly **not yet implemented** server-side. Build firmware
defensively around them (i.e., don't rely on the server enforcing/providing
them), and expect this document to be updated when they land:

1. **No active per-device topic ACL.** The broker's `acl_file` (which would
   restrict a device's certificate to only its own `rmp/v1/{deviceId}/...`
   topics) is present in config but **commented out**. Right now, any
   client holding a valid cert signed by the platform CA can technically
   publish/subscribe to any device's topics. Don't build security-sensitive
   firmware logic assuming the broker is policing this yet.
2. **No automated certificate issuance/CN↔deviceId binding.** Certs are
   currently generated by a dev script, not a factory pipeline. The
   "CN should equal deviceId" rule is intended but not validated anywhere.
3. **`cfg/desired`'s `thresholds`, `alertCatalog`, `calibration`, `network`
   fields are always `null`.** Don't build logic expecting real values here
   yet.
4. **Calibration apply/rollback status is optimistic.** The backend marks a
   calibration "APPLIED" the moment it sends the `set_calibration` command —
   it does **not** currently wait for or verify your `ack/cmd` response
   before considering it applied. Send the ack anyway (for the audit trail
   and future-proofing), but don't expect the server to retry or roll back
   automatically if you reject it today.
5. **`TIME_ANCHOR` does not back-fill previously-unsynced samples.** If a
   device sends 50 samples unsynced (`tsync:0`) and then syncs and sends a
   `TIME_ANCHOR` event, the previous 50 samples remain flagged
   `TIME_UNSYNCED` with server-receipt timestamps — they are not
   retroactively corrected.
6. **Alarm severity from device data is always `WARNING`.** There is no
   `CRITICAL` classification path wired up from threshold evaluation yet,
   regardless of how far out of range a value is. This doesn't affect what
   firmware needs to send — just don't expect to see `CRITICAL` alarms yet
   if you're cross-checking against the web UI.
7. **Device-claim auto-registration.** Claiming an unrecognized `serialNo`
   today creates a new device record on the spot rather than requiring
   pre-provisioning. This is flagged as a dev convenience, likely to be
   tightened before a real factory rollout — don't build a firmware-side
   assumption that any `serialNo` will always be auto-accepted.

## 10. Quick Reference — Minimal Connect Sequence

1. Connect to the broker over mTLS, MQTT5, with your issued client cert/key
   and the platform CA cert.
2. Subscribe: `rmp/v1/{deviceId}/cmd/+`, `rmp/v1/{deviceId}/cfg/desired`.
3. Publish `state` (retain optional) with `online: true`.
4. If you have a time source, sync and publish a `TIME_ANCHOR` event.
5. Start publishing `tele/batch` messages as samples accumulate, with an
   honest `tsync` flag every time.
6. Handle `ack/data` (optional — informational) and any `cmd/{name}`
   messages, replying on `ack/cmd` with the same `id`.
7. On reconnect after an outage, replay buffered samples via `tele/backlog`
   (same shape as `tele/batch`), tagging rows `STARTED_OFFLINE`/`LINK_DOWN`
   as appropriate via the `fl` bitmask.
